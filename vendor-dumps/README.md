# vendor-dumps

Full flash images pulled off real cameras, for booting as QEMU `flash-file=`
digital twins. The dump binaries (`vendor-dumps/*.bin`) and the boot logs
(`vendor-dumps/*.log`, regenerated by the run scripts) are gitignored; the small
`SHA256SUMS` and `api-responses-*.txt` reference files are tracked. Obtain the
dump separately (see the pull recipe below / `SHA256SUMS`), then run the scripts
in `qemu-boot/`.

## ipc8232swc-we-vendor-nand-128mib-20261119.bin

**Device:** Rostelecom **IPC8232SWC-WE-B** (Uniview C1L-2WN rebadge) —
HiSilicon **hi3516ev300** + SuperPix **SP2305**, running **stock vendor
firmware** (VC-HAL + AgentGreen, FW v5.8.0-b575710). Lab unit at `10.216.128.89`.

**Flash:** Winbond **W25N01GV** SPI-NAND, 128 MiB, main-page data only (no
OOB/ECC — `nand read` returns page data without spare bytes).

**sha256:** `7a2fd662ae420827c048619398dad5ae8335b471c27389ca727bfa9804d59387`

### Contents (binwalk-style scan)

| Offset | Thing |
|---|---|
| `0x0047d0` | gzip vendor U-Boot (U-Boot 2016.11) |
| `0x200000` | uImage `Linux-4.9.37`, load/entry `0x40008000`, ~5.25 MB |
| `0xa00000` | UBI (erase + volume headers; UBIFS rootfs) |
| `0x2cd2200`→end | erased `0xff` (chunk crc `86175ebf` per 16 MiB) |

Real content occupies the first ~44.8 MiB; the rest is blank NAND.

### How it was pulled (non-destructive, no flash write)

UART on `/dev/ttyUSB0`, USB power via `micro-01` (switches project). The vendor
U-Boot 2016.11 lacks `tftpput` and its MMC won't init, so OpenIPC's own U-Boot
was **side-loaded into RAM over the HiSilicon bootrom** with `defib`, then its
`tftpput` streamed the NAND out over the network. Flash was never written — a
power-cycle returns the camera to stock (verified: `.89` came back up).

1. `defib burn -c hi3516ev300 -p /dev/ttyUSB0 -f <universal-uboot> -b`
   — **must** be the *universal* build (`u-boot-hi3516ev300-universal.bin`);
   the default *NOR* build has no `hifmc100` NAND driver / `nand`/`tftpput` for NAND.
2. Host WRQ TFTP receiver on `:69` (stock `in.tftpd` is RRQ-only).
3. In U-Boot: `dhcp`; `setenv serverip 10.216.128.229`; then per 16 MiB chunk
   (0…0x8000000): `nand read 0x42000000 <off> 0x1000000` → `crc32` →
   `tftpput 0x42000000 0x1000000 <host>:nand_<off>.bin`, verifying each chunk's
   U-Boot crc32 against the host file. All 8 chunks matched.
4. Assemble the 8 chunks into the single image this repo expects, in offset
   order, and verify against `SHA256SUMS`:

   ```sh
   cat nand_00000000.bin nand_01000000.bin nand_02000000.bin nand_03000000.bin \
       nand_04000000.bin nand_05000000.bin nand_06000000.bin nand_07000000.bin \
       > ipc8232swc-we-vendor-nand-128mib-20261119.bin
   sha256sum -c SHA256SUMS      # expects 7a2fd662…d59387
   ```

Scripts used: `scratchpad/dump/{tftp_wrq.py,dump_uboot.py}` (session artifacts).
Full procedure + the no-UART-install analysis: `~/projects/cameras/rostelecom/docs/`.

### Booting the twin

The NAND model already matches this chip (`run-ev300-nand.sh` presents
`nand-jedec=0xEFAA21` = W25N01GV):

```sh
FLASH=vendor-dumps/ipc8232swc-we-vendor-nand-128mib-20261119.bin \
  bash qemu-boot/run-ev300-nand.sh
```

With `flash-file=` and no `-kernel`, the synthetic boot ROM runs the camera's
**own** BST/BLD/U-Boot from NAND.

**Boot verified 2026-11-19** (`boot-20261119.log`): vendor **U-Boot 2016.11**
detects the W25N01GV, loads the vendor `uImage Linux-4.9.37` from NAND and boots
it; the kernel creates the 5 vendor MTD partitions (boot/tech/kernel/app/config),
attaches **UBI** on `mtd3`, and reaches vendor userspace.

**With the SP2305 attached** (`boot-sensor-sp2305-20261119.log`) it goes much
further. `run-ev300-nand.sh` passes `sensor=none` (for OpenIPC); boot the vendor
image with **`sensor=sp2305`** instead — use `run-ipc8232-vendor.sh`:

```sh
bash qemu-boot/run-ipc8232-vendor.sh          # FLASH + sensor=sp2305 defaulted
```

The `hisi-sp2305` I2C stub (bus 0 `0x12060000` @`0x3C`, chip id `0x2735`) ACKs
the driver's writes — the `hi_sensor_i2c_write … ret=-5` flood is gone — so the
kernel logs `SNS: is [sp2305]!`, loads `libsns_sp2305.so`, inits the ISP
(`/dev/hi_mipi initialized`), and the full **VC/AgentGreen** stack
(Agent-Updater, VC-SYS-Daemon, InterConn, App `v4.0.0-b575710`) comes up to the
**QR-provisioning** state of an unbound camera.

**VI interrupt fix (2026-11-19, `boot-sensor-sp2305-vi-fix-20261119.log`).**
With the sensor attached the vendor ISP runs **offline** (`online_flag=0`), and
the VI capture IRQ (SPI 43, Linux virt #41) was being **disabled** by the kernel
(`irq 41: nobody cared`). Cause, in `hw/misc/hisi-vi.c`: `vi_frame` sets
`WCH_INT_EARLY` (bit 15, a VPSS-only "lines-in" signal) every V4 frame, and
`vi_cap_status` synthesized the pipe-0 summary bit (`CAP_INT`, 0x100) from *any*
nonzero `CAP_WCH_INT(0)`. The vendor ISR clears frame start/end (bits 0/1) but
not EARLY, so offline — where no online VPSS consumes EARLY — the summary bit
stayed set and the IRQ re-fired forever. Fix: synthesize the summary bit from the
serviceable bits only (`WCH_INT_FSTART | WCH_INT_FEND`). After it, the IRQ is
handled and the agent advances to full stream/upstream setup (H264 Main 1280x720,
SpifPacketizer, SetUpstreamParams).

### Reachable via the Rostelecom `/api/v2` API (2026-11-19)

The twin is now reachable over AgentGreen's local API, exactly like the unlocked
real camera. `qemu-boot/run-ipc8232-vendor-api.py` automates the non-destructive
unlock over the emulated console (interrupt U-Boot → `rdinit=/bin/sh` →
`export AG_FORCE_DIRECT_ACCESS=1` → `exec /sbin/init`) and forwards host ports to
the guest's API/RTSP:

```sh
uv run --with pexpect python3 qemu-boot/run-ipc8232-vendor-api.py   # holds open
# from the host:
curl -s --digest -u admin:admin54321 http://127.0.0.1:18080/api/v2/device/info
```

Live, authenticated (`admin:admin54321`), authentic data from the dump
(`api-responses-20261119.txt`):

| Endpoint | Result |
|---|---|
| `GET device/info` | 200 — model `IPC8232SWC-WE`, vendor uniview, fw `v5.8.0-b575710`, agent `v6.9.0` |
| `GET device/{status,uid,capabilities}` | 200 |
| `GET system/uptime`, `system/network/interfaces` | 200 |
| `GET stream/{encoding,channel_id}`, `image/capabilities` | 200 |
| `POST system/network/ping {"hostname":"x | id"}` | 200 → `uid=0(root)` (the vendor RCE, reproduced) |
| `GET stream/snapshot` | **500** — `HI_MPI_VPSS_GetChnFrame() failed 0xa007800e` (frames gap, below) |

Ports: host `18080→8080` (API), `18081→80`, `15540→554` (RTSP). The guest is on
QEMU user-net (`10.0.2.15`); `-nic user,restrict=on` is dropped so hostfwd works.

**Current floor:** still `No video frames` — no pixels are delivered. In this
offline config the driver should start `VI_PROC` per captured frame
(`PROC_START`, 0x300) and drive VPSS, but it writes neither (`PROC_START` count
0, VPSS barely touched, no `REGUP`). The model's offline capture→pipe-start→VPSS
handshake isn't being triggered by the vendor VC-HAL (its offline MPP sequence
differs from the OpenIPC path the model was tuned to). Modelling that handshake —
the captured-frame bookkeeping the ISR checks before starting the pipe, then
VPSS painting and VENC encoding — is the remaining work to get a streamed frame.
